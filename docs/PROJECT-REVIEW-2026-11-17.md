## 优先处理的实现问题

### 1 分析使用的范围可能与屏幕选择不一致

**P1，已确认。** [ImportDetail](../frontend/src/App.tsx#L111-L127) 把文件勾选和 PDF 页码存在局部状态，只有“保存范围”才发出 PUT；“分析材料”仅提交 `focus`。[MaterialAnalysis](../frontend/src/MaterialAnalysis.tsx#L29-L50) 继续使用已保存记录显示覆盖量和职业入口，没有判断范围是否修改但未保存。

用户取消勾选文件或缩短页码后直接分析，实际仍会使用旧范围；已有分析时也可直接按旧结果创建冒险。这会造成学习范围误解，且可能发送用户以为已经排除的内容。本次未向模型发送材料复现。

建议把范围草稿与生效范围明确关联：保存或明确丢弃改动后才能分析或创建冒险，也可采用清楚标示的“保存范围并分析”。验收需覆盖文件取消勾选、PDF 页码、保存失败和已有分析四种情况，确认实际提交给模型的批次内容与用户最终确认的范围一致。

### 2 评审中断可能留下新回答和旧评审

**P1，已确认持久化窗口，崩溃场景未实测。** [answer](../backend/adventures.py#L294-L329) 先保存 `last_answer`，随后调用模型，最后才保存 `last_evaluation` 和 `attempts`。第一次写入没有标记本次评审状态或绑定尝试 ID。[启动恢复](../backend/adventures.py#L40-L51) 处理分析、规划和生成中断，没有处理评审中断；[前端](../frontend/src/App.tsx#L82-L83) 优先恢复浏览器草稿、否则读取最新回答，同时独立加载旧评审。

若进程在两次持久化之间异常退出，新的回答可能继续显示上次通过的评审，该次尝试也未进入日志。普通模型异常已被捕获并保存为待评审；这里的问题是结果写入前的进程中断。

建议在请求模型前持久化独立尝试及待评审状态，结果按尝试 ID 结算；重启后明确显示中断并允许手动重试。验收应在隔离存档中中断首次提交和重复提交，确认回答保留、状态归属正确、不自动发起模型调用，既有目标完成记录不被误改。

### 3 替代任务失败会让原题退出正常入口

**P1，已确认。** [prepare_task](../backend/adventures.py#L243-L285) 在生成替代题前就把原题设为 `archived=True` 并保存；后续失败只把新题标记为失败，没有恢复原题。[public](../backend/adventures.py#L102-L113) 隐藏归档题，因此原题虽仍保存在本地，正常界面已不能继续进入。

建议让原题在候选题生成、校验成功前保持可用，再一次性发布替换关系；或提供明确的回到原题操作。验收覆盖超时、格式错误和改变公开标准的替代结果，保证原题、回答及练习仍可访问；成功替换继续保留历史，并保持既定公开标准及所要求的执行入口不变。

### 4 代码任务发布前未核实执行入口和能力

**P1，已确认校验缺口，具体模型触发频率未测。** [任务发布](../backend/adventures.py#L261-L280) 对非空 `run_entry` 做相对路径安全检查后即可发布 `code` 任务，没有验证入口存在、适配器是否支持或本机工具是否可用。首次任务会将执行要求写入目标契约，而[替代题检查](../backend/adventures.py#L275-L277) 禁止改变已要求的入口。[runner](../backend/runner.py#L341-L370) 已有只读执行能力查询，可作为基础复用。

如果模型指定不存在或无法执行的入口，玩家仍须成功运行才能通过，重生成替代题又不能直接纠正契约；缺少工具链和入口本身错误还需要不同处理。后端并没有伪造运行成功，但恢复路径不完整。

建议区分入口有效性、工具可用性和实际执行结果：错误入口不要发布；首次发布前发现缺少工具时，提供明确说明和符合目标的理解或推演路径，系统安装仍须确认。已发布目标的恢复方案需明确处理契约和既有进度；普通替代题仍须保持既定公开标准及所要求的执行入口不变。验收至少覆盖空入口、缺失文件、不支持的文件类型、缺工具和有效入口，并确认可访问的编辑文件与执行要求匹配。空入口目前允许用户手选，应检查是否存在可发现、可用的选择，不必一律拒绝。

### 5 指定重启端口被占用时会先停掉旧实例

**P1，已确认顺序，未执行重启复现。** [_restart_managed](../backend/runtime.py#L295-L308) 先调用 `_stop_instance`，随后才检查目标端口是否被占用。服务运行在 A 端口、用户要求切到被其他程序占用的 B 端口时，可预先识别的失败会发生在原服务已停止之后。

建议提前验证不同于当前服务端口的显式目标端口，保留停止后的再次检查以处理竞争。验收使用隔离实例：B 被占用时明确报错，A 的实例 ID 和健康状态保持不变；不终止占用 B 的其他程序。同端口正常重启也需保留覆盖。

### 6 旧目录清理缺少归属证明

**P1，已确认条件风险，没有检查或发现实际用户数据受损。** [应用初始化](../backend/api.py#L52-L56) 调用 [cleanup_legacy](../backend/legacy_cleanup.py#L13-L42)。它对链接和越界有防护，但只凭数据根目录下的 `workspaces`、`imports`、`diagnostics` 等名称决定删除，未验证它们确为本项目受管理的旧副本。

默认独立存档目录符合预期；若 `CODEWARDEN_DATA` 指向混有用户原文件的目录，同名目录也会进入删除集合。[现有测试](../tests/test_legacy_cleanup.py) 验证了数据根之外的原文件保留，尚未覆盖数据根内同名非受管目录。文件删除和数据库清理分步进行，中途失败也需考虑恢复。

建议用可验证的旧状态记录或所有权标记限定删除对象；无法确认归属时停止清理并说明原因。验收仅用合成目录，覆盖合法旧副本、无归属同名目录、链接和中途失败，确保原始文件、模型设置及凭据保留。无需恢复旧版界面，也不改变已经授权的历史废案清理方向。

## 学习与游戏体验需要补齐的部分

### 7 已完成任务缺少干净的再次回忆流程

**P1 产品缺口，已确认。** [_refresh](../backend/adventures.py#L157-L167) 只从未完成任务中推荐，自评“还需复习”不会把已完成任务重新纳入推荐。[回忆日志](../frontend/src/App.tsx#L107) 是展示列表，没有直达任务的入口。重新打开旧题时会恢复旧答案、提示和评审；“先尝试回忆”只控制讲解显示，无法形成不看历史答案的再次作答状态。

建议先做当前角色内的待复习入口和新的回忆尝试，不急于设计复杂记忆算法。已完成、标记需复习的目标应能直达；历史答案、提示和反馈默认收起，用户主动展开才显示。保留目标首次完成和历次尝试，近期掌握程度独立记录，不跨角色继承。

验收关注玩家是否能从营地找到需要复习的内容、在不看旧答案时重答并获得反馈；完成数不因复习重复累加。之后再依据实际使用引入间隔调度。

### 8 练习状态和排序答案不够直观

**P2，已确认界面实现。** [任务界面](../frontend/src/App.tsx#L93-L108) 的代码编辑先存浏览器草稿，运行使用已保存副本；保存修改后，上一次成功输出仍可显示。后端已有[副本版本核验](../backend/adventures.py#L301-L318)，但前端没有清楚呈现“未保存、已保存待运行、当前版本已运行”的区别。

同一界面的排序题依靠勾选时序把选项 ID 写入文本框，选项仍按原顺序展示，没有带选项文本的答案顺位和直接调序操作。

建议呈现副本与运行证据的对应关系，保留历史输出并标明已过期；运行前说明未保存草稿不会生效。排序题提供可读顺序和键盘调序。验收覆盖未保存、保存后未重跑、失败与成功运行、重开排序草稿，避免把工具操作困难混同为知识不理解。

### 9 日志把当前自评附到全部历史尝试

**P2，已确认。** [reflect 和 journal](../backend/adventures.py#L330-L348) 每题只保存一份当前自评，读取日志时将它附到该题所有历史尝试上。[前端](../frontend/src/App.tsx#L107) 在每条历史回答下展示这份自评，容易让读者以为它代表当时的理解程度。

建议明确选择语义：当前自评只在任务级单独展示；若要支持学习变化回顾，则从新记录开始保存带时间的自评事件或当次快照，不重建并不存在的历史。验收为同题两次回答、两次不同自评，过去记录不被最新自评伪装成当时状态。

### 10 游戏反馈与知识成果的连接仍可加强

**P2 产品建议。** [营地与冒险](../frontend/src/App.tsx#L101-L108) 已显示称号、完成数、推荐任务和纪事，但推荐主要是列表内标记，提交后产生的解锁和纪事位于任务窗背后的冒险页。现有职业形象和开场资产可以继续使用。

建议让冒险页面提供明确的“继续探索”或推荐目标入口，在作答反馈中展示本次实际解锁的目标、形成的纪事和可选下一步；职业差异更多体现在理解概念、推演脚本、追踪代码、分析架构和解释历史的任务方法上。保持其他已开放任务可选，不增加无关的线性关卡、统计面板或装饰性口号。

验收用一条真实学习过程判断：玩家能说明当前学什么、为什么值得做、完成后发生了什么，以及接下来能去哪里。没有真实解锁时不制造奖励或成长结果。

## 质量风险与工程推进条件

### 评审依据和代码证据预算需要更精确

**P2，已确认。** [评审校验](../backend/adventures.py#L319-L327) 要求检查项覆盖全部公开标准，但对 `evidence` 只检查字符串类型。每项都标记通过、依据却为空或空白的合法结构仍可能使目标完成。建议先拒绝空依据，再用固定样本检验依据是否对应材料和回答；非空字符串本身也不能证明判断正确。

另一个明确限制是 [_changed_code](../backend/adventures.py#L349-L365) 把整个修改后文件放入总计 12,000 字节的 JSON 预算。合法长文件即使只改一行，也可能无法评审，“缩小修改范围”不能准确说明原因。建议使用带文件位置的差异和必要上下文，仍绑定同版实际运行；验收覆盖长文件小改动与真正证据超限，不能用静默截断伪装为完整证据。

### 材料读取完成与知识覆盖仍需分别衡量

材料分批读取与断点继续已有实现；当前风险在后续摘要和规划。[分析校验](../backend/material_analysis.py#L41-L70) 验证引用来自允许的来源，但不要求汇总保留每个输入批次或重要主题；[末级汇总完成后](../backend/material_analysis.py#L199-L222)即保存完成状态，[规划上下文](../backend/material_analysis.py#L236-L257)主要来自最终概览。某批来源若在汇总中消失，后续规划可选来源会随之缩小。

这是源码可确认的约束缺口，不代表本次已观察到模型遗漏，也不意味着每段文字都必须出题。建议保留批次到主题的来源覆盖关系，区分“已读取”“已纳入主题”“本轮未选为学习目标”，用覆盖材料首尾、跨批关联和不同职业的样本验证。

现有结构校验和模拟模型测试不能证明讲解准确、答案不泄露、等价回答能通过或错误回答能被拒绝。下一轮应建立小规模固定材料和人工预期，用用户已配置的兼容模型单独验收；模型运行成本、结果与本地测试分别记录，不将 AI 自评当成人工质量结论。

### 前端与跨平台验证尚未形成统一入口

仓库已有六个前端测试文件和较多后端测试。本次前端 19 项通过，但 [package.json](../frontend/package.json) 没有测试脚本，[README 开发检查](../README.md#开发检查) 只列后端 pytest 和前端构建；版本控制内没有 CI 工作流。组件测试使用模拟 React 钩子或 DOM，[browser_fixture.py](../tests/browser_fixture.py) 提供合成模型服务，不等于已维护完整浏览器用例。

建议在一套明确的检查入口中纳入现有前端测试、后端测试、类型检查和构建，再增加真实浏览器主流程。重点覆盖范围保存、双角色切换、任务替换失败、重复回忆、排序及键盘焦点。另有待浏览器验证的路径：[延迟日志请求](../frontend/src/App.tsx#L97) 返回时不检查导航上下文，可与已打开的[任务对话框](../frontend/src/App.tsx#L107-L108)同时挂载；两个对话框的全局键盘监听可能竞争。

Windows 和 macOS 均有启动脚本及凭据适配，但 README 已明确 macOS 待实机验证。需要在隔离档案中验证干净安装、凭据跨进程读写、启停恢复及 Java、Python、JavaScript、TypeScript、Go、Bash、POSIX sh 的实际正反用例。缺工具导致的跳过应单独报告，不能算已验证支持。

### 安装预检和代码组织可降低后续维护成本

[Windows 安装脚本](../setup.ps1#L3-L7)和[macOS 安装脚本](../setup.sh#L4-L8)检查命令存在后即开始创建环境，没有先验证声明的 Python 3.11+、Node.js 22+ 版本。建议在写入前给出准确版本诊断；不自动安装系统工具。

[App.tsx](../frontend/src/App.tsx) 将导航、导入、设置、日志、任务、编辑和运行集中在 129 行内，最长一行约 5,465 个字符；后端冒险模块也同时承担规划、任务、评审、成长和日志。问题是多种状态转换难以独立审查，而非单纯代码行数。建议围绕本次确认的问题逐步拆分导入范围、任务尝试、练习状态和模态导航，不先进行大规模技术栈替换。

长材料的时间与调用成本也值得进一步呈现：[模型客户端](../backend/model_client.py#L294-L339) 已记录请求大小、耗时和服务商返回的 token 用量，因此不是从零增加诊断。可将这些信息关联到具体操作，先展示已发生的调用和耗时，再考虑显式暂停或停止；继续遵守刷新、重启和切换角色不自动调用模型的边界。

## 可以选择的推进方向

| 方向 | 能解决什么 | 取舍与建议 |
| --- | --- | --- |
| A 稳定一次完整学习过程 | 输入范围、评审归属、替代失败、代码入口与运行恢复 | 优先推荐。先降低完成主流程时遇到错误状态和死路的机会，视觉变化较少。 |
| B 建立持续回忆与职业成长 | 完成后还会再回来学习，成长与实际知识成果相关 | A 之后优先。先做待复习和再次回忆，再考虑调度；避免只增加称号和数值。 |
| C 加强探索中的游戏反馈 | 推荐入口、任务成果、主题变化和职业差异更容易感知 | 可在 A 稳定后与 B 配合；依赖真实进度事件，不单独推进装饰性场景。 |

测试与平台验收贯穿三个方向。暂不建议扩展新职业、云同步、多人玩法、旧档案兼容层或自动系统安装；当前已有能力更需要完成可验证的学习闭环。

## 建议的实施顺序与验收结果

| 阶段 | 建议范围 | 完成标准 |
| --- | --- | --- |
| 1 一致性与恢复 | 问题 1–6，代码版本提示与评审证据校验；为修复补有意义的回归用例 | 界面范围与请求一致；评审绑定当次回答；替代失败原题可用；无效入口不形成死路；空依据不能通过；可预检的重启失败保留旧实例；清理只作用于确认归属的旧数据。 |
| 2 可重复的学习过程 | 问题 7–9，排序与日志入口 | 已完成任务可从待复习进入干净回忆；历史记录不失真；角色隔离与首次完成计数保持正确。 |
| 3 知识成果驱动游戏反馈 | 问题 10，职业任务样本、来源覆盖 | 玩家能看见真实解锁和下一步；职业教学方法可区分；被选中材料的遗漏能够说明或定位。 |
| 持续发布验收 | 统一检查入口、浏览器主流程、Windows/macOS 与真实模型样本 | 测试通过、跳过、未测分别记录；端到端行为、平台工具与教学质量各有证据，不互相替代。 |

每个阶段先把范围落实到具体修复或功能方案，再按项目约定确认实施。独立角色、本地运行、练习副本、原始文件与凭据保留、用户自行配置接口，以及 AI 与真实执行结果分开标示，继续作为验收边界。
